# 多群巡场与发消息 · 通道分工手册（2026-09-15 定）

> 起因：要在多个小红书群之间巡场、陪聊，对比了「豆包自带 GUI 浏览器」和「自写 CDP 脚本」两条路，亲手实测后定下分工。结论先行：**没有谁取代谁，按活儿切换——广而轻用浏览器，深而稳用脚本。**

## 一、两条通道各自的脾气

### A. 豆包自带浏览器（GUI：打开网页 + 截图 + 点击/输入/回车）
- 强在「广」：
  - 一屏总览整个会话列表，每个群的未读红点、最新一句预览都看得见，**多群"看哪里在@我、哪里有活"最强**，不用一个个切；
  - 所见即所得：点输入框 → 打字 → 回车就发，短句轻聊最省事，不用写代码；
  - 带着登录态，和 CDP 脚本那一侧是同一账号、消息实时同步，不冲突。
- 弱在「深」：
  - 读长聊天要一屏屏截图翻，慢、容易看不全，读到的是画面不是整段文本；
  - 每步都是"截图→看图→操作→再截图"，来回轮次多；
  - contenteditable 富文本输入理论上可能丢焦点，超长文、发后逐条查重不如脚本确定。

### B. CDP 脚本（读：工具/read_group_stable.py；发：工具/xhs_im.py）
- 强在「深、快、稳」：
  - 直接取消息列表的文本，长上下文一把读全、读得快、可连贯爬楼；
  - 内核注入（insertText）稳定，注入后逐字读回校验，发完直接数正文消息块做唯一查重；
  - 适合深读上下文、发长文、任何要确定不发重/不发残的稳活。
- 弱在「巡场」：
  - 一次钉在一个会话里，多群要逐个导航切换，"一眼看全所有群"不直观；
  - 要写/跑脚本，机械步骤多，高频轻聊反而重。

## 二、定下来的分工（照此执行）

| 场景 | 用哪条 |
|---|---|
| 多群巡场、扫谁@我、看未读、轻松短句陪聊 | **自带浏览器**（眼睛/雷达，广、省事、耐久） |
| 进某个群深读长上下文、爬楼梯补前情 | **CDP 读群脚本**（一把读全） |
| 发长文、正式回复、要稳定注入和发后查重 | **CDP 发送脚本**（确定、可核验） |
| 一次性看个外部网页/登录/点界面 | 自带浏览器，不必现写脚本 |

两者同一账号、消息同步：浏览器里发的，脚本能读到；脚本发的，浏览器也看得到。按活切换即可，不重复发同一条。

## 三、一条被实测推翻的旧判断
原先凭印象觉得"自带浏览器读群更累、只配干一次性网页的活"。亲手开下来要修正：它在**多群总览 + 随手轻聊**上恰恰最省，日常陪阿阮逛群优先用它。**通道选型不许凭印象，要亲手试了再定。**

## 四、配套技术事实（便于以后复用）
- 网页版会话列表是 Vue 渲染的 `div`，不是普通 `a` 链接：会话项选择器 `.xhs-im-conv-item`，群名 `.xhs-im-conv-item__name`，未读红点 `.xhs-im-conv-item__badge`；换群=点对应会话项，再从地址栏读当前会话。
- 消息流容器 `.xhs-im-msg-list`（懒加载，要反复滚到底才读得全）；输入框 `.xhs-im-input-bar-editor` 是 contenteditable 富文本，不是 input/textarea。
- 用读群脚本做"是否发重"核验时，要先排除脚本自己开头打印的 `[末尾指纹]` 行（它会复述最后一条），只数正文消息块（已同步写进《豆阿辰读群与对外发言SOP》）。
- 家里另有一个私房"秘密群"（成员：豆阿阮、豆晚风=阿晚姐、宁九=阿九姐；后两位是 9·19 婚礼主婚人）。多群操作时发送前务必认准当前会话，**严防发错群**。

## 五、不变的红线
对外只用"豆阿阮"，真名不出现在任何对外/公库内容；群消息单条≤500、纯文本（不用星号井号）、带【1号窗】；发前自查、发后刷新核验只此一条；图片/视频由阿阮代发；登录只走 App 扫码点确认，绝不刷短信验证码。
